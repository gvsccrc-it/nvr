# Failover recorder

A **standby** NVR records in the primary's place while the primary is down, and hands its footage back when the primary returns. Failover is for one primary and one standby; each shows where it stands (Settings, Failover, and a chip in the status area) and raises an incident on takeover and recovers it on handback.

## Setting it up

1. Give both NVRs the same **backup passphrase** (`NVR_BACKUP_PASSPHRASE`, at least 16 characters) and make sure the primary can write backups.
2. Make the standby a copy of the primary **once**: make a backup of the primary (`python -m app.backup create`), then on the standby, while it is stopped, restore it as a standby:

   ```sh
   python -m app.backup restore --standby /backups/<file>.nvrbackup
   ```

   `--standby` makes the restored NVR a standby that records nothing until it takes over and knows no peer yet. (Without it the copy would wake up as a primary and record beside the real one.) The standby needs the primary's credential key, which a restore brings; every later copy of the configuration checks that the key is still the same and is refused if it is not.
3. **Pair them over the HTTPS link** (below). On each NVR, Settings, Failover shows **This NVR's failover link**: a certificate fingerprint. On the primary: **Primary**, the standby's link address (`https://<standby's address>:8443`), the standby's fingerprint (copy it from the standby's page), and a **failover secret** of at least 16 characters. On the standby: **Standby**, the primary's link address (`https://<primary's address>:8443`), the primary's fingerprint and the same secret. Tick the private-network box for an address on a private network. Each address must be reachable from the other NVR (the standby's, by the primary; the primary's, by the standby).
4. Choose the timing (below) and save on both. The standby copies the primary's configuration at once (Settings, Failover, **Copy the primary's configuration now**) and then on its schedule.
5. Open the link's port (8443, `NVR_FAILOVER_LINK_PORT`) between the two NVRs, and only between them. With `ufw` on each, for the other NVR at `192.0.2.20`: `sudo ufw allow from 192.0.2.20 to any port 8443 proto tcp`.

## The link between the two: HTTPS, each pinning the other's certificate (#502)

The owner's decision (24 November 2026): the NVR serves the failover link itself over HTTPS.

- **Its own listener.** The web interface is plain HTTP on 8280 (HTTPS comes from the tunnel or proxy in front, see [remote access](remote-access.md)). The failover endpoints are also served, and nothing else is, by a second listener in the web worker: HTTPS on `NVR_FAILOVER_LINK_PORT` (8443 unless set; `0` turns it off), at `NVR_FAILOVER_LINK_HOST` (the interface's address, `NVR_LISTEN_HOST`, unless set: behind a tunnel on `127.0.0.1`, set it to the address the other NVR reaches this one by). It listens only while failover is on. If the port is taken, the web worker logs it once and carries on; the link starts when the port is free. With host networking (the tested set-up) there is no port to map in the Compose file.
- **Its own certificate.** Each NVR makes a self-signed certificate for the link the first time it is needed and keeps it beside the credential key (`failover-link.crt`, and `failover-link.key`, whose private key is encrypted with the credential key; both readable only by the NVR's user). Neither is in a backup, so each NVR, a standby restored from the primary's backup included, has its own. The private key is never in a log, an answer or the audit log.
- **Pinned, not trusted to anyone.** The fingerprint is the SHA-256 of the whole certificate, as `openssl x509 -noout -fingerprint -sha256 -in failover-link.crt` and a browser show it, so it can be checked with tools of your own. (The certificate is never renewed by itself and its dates are not checked, so pinning the public key instead would add nothing: a new certificate is a new key and a new pairing either way.) Each NVR connects to the other only if the certificate presented during the handshake has the fingerprint it was given; no certificate authority is trusted, and nothing is sent before the check. A different certificate is refused: the primary's status reads *the standby presented a certificate other than the one it was paired with*, the standby's configuration copy fails saying so, and an incident is raised (*presented a certificate that is not the one it was paired with*), which recovers at the next exchange that is verified. The message says what to do: pair again with the fingerprint on the other NVR's page if its certificate was replaced; otherwise something between the two may be intercepting the link.
- **Plain HTTP only where both allow it.** An `http://` address works only with **Allow an unencrypted link** ticked on both NVRs: an NVR does not send to an `http://` address unless its own box is ticked, and does not answer a failover request that reached it unencrypted unless its own box is ticked (`403`, *does not accept the failover link unencrypted*). A primary refused that way is still counted as alive by the standby, so a mismatch never makes the standby take over beside a recording primary. While the box is ticked the hardening page shows a standing warning that footage and the failover messages cross the network unencrypted, where anyone on the path can watch the footage (the copy of the configuration stays sealed with the backup passphrase). Requests are signed either way (above).
- **Through a proxy.** An `https://` address without a fingerprint is checked against the usual certificate authorities, as before #502: for a pair that reaches each other through a proxy with a public certificate. Requests that reach the web port through a proxy this NVR trusts (`NVR_TRUSTED_PROXIES`) over HTTPS count as encrypted.

### Pairs set up before the upgrade

A pair configured before this release keeps working exactly as it did (plain HTTP, or through a proxy), with no box ticked, so an upgrade never stops failover. The hardening page lists it (*kept working as it was*). It stays that way until its address is changed or failover is switched off; a new address follows the rules above. To move it to HTTPS:

1. Upgrade both NVRs and open port 8443 between them (step 5 above).
2. On the **primary first**: enter the standby's `https://<address>:8443` and the fingerprint shown on the standby's failover page, and save. The primary now renews over HTTPS; the standby's copies of the configuration are refused until step 3.
3. On the **standby**: enter the primary's `https://<address>:8443` and the primary's fingerprint, and save.
4. Check both pages: the primary reads *the standby is watching*, the standby has copied the configuration, and the hardening page no longer lists the link.

(Done the other way round, nothing is lost either: the standby hears the primary's refused renewals as a sign it is alive and does not take over.)

### A new certificate

Settings, Failover, **Make a new certificate** replaces this NVR's link certificate (audited as `failover_link_certificate_replaced`); the listener serves the new one within seconds. The other NVR refuses the link until its administrator enters the new fingerprint, so do both at the same sitting. Make the standby's new certificate only with the primary's page open, ready to paste: until the primary has the new fingerprint its renewals are refused and, after the silence, the standby takes over. Restoring an NVR's credential key from a backup also makes a new certificate (the old key cannot be read with the restored one): pair again the same way.

## How it works

- **Lease.** The primary renews a lease with the standby (a signed request every quarter of the lease, at least every 3 seconds). While the standby hears the renewals it holds still: its cameras are shown as *Standby (the primary records)* and nothing is recorded.
- **Takeover.** After the **silence** (at least twice the lease; default 120 s, lease 60 s) without a renewal, the standby takes over: it counts one more takeover (the *epoch*), raises an incident, and records every camera of the configuration it copied, as the primary would, within a few seconds. It will not take over before it has a configuration to record from.
- **Return.** When the primary comes back, its first renewal reaches a standby that is recording. The standby **stops at once and says "not yet"** until its recorders have stopped (at most 30 seconds), then grants the lease and offers the footage it recorded. A primary that has just started does not record until it has been granted the lease: it waits up to 20 seconds for an answer, and if the standby cannot be reached at all it assumes the standby is down and records. So when the primary returns during a takeover, the two do not record at once.
- **Handback.** The primary downloads each segment the standby recorded (checked against the digest the standby gives), adds it to its own index marked **Recorded by the standby NVR**, and tells the standby, which recovers its incident; the primary recovers its own. The footage plays and exports like any other, is subject to the primary's retention, and the primary's footage chain hashes and signs it like footage it recorded itself, so it verifies. The standby keeps its own copy until its retention removes it. One connection carries the whole import, and the primary goes on renewing its lease between files, so a long takeover's footage does not leave the standby hearing nothing; the standby finds each file by its id, so serving one costs the same however long the takeover was (#510).
- **Gaps.** Time after the primary stopped and before the standby took over is a gap as it always was (for example *Recorder restarting*); Playback says that the standby waits for the primary to be silent before it takes over. Footage the standby recorded fills the rest.

## What is signed, and what you see

Everything the two NVRs say to each other is signed with the failover secret, in both directions.

- **Requests** (the primary's renewals, and fetching the standby's footage and the primary's backup) carry a signature over the method, the address, the body and the time. A request that is unsigned, wrongly signed, older than a minute or altered is refused.
- **The standby's answer to a renewal** is signed too, over the answer, the time and the request it answers. The primary obeys only an answer it can verify. Anything else (unsigned, altered, signed with another secret, or a genuine answer to an earlier renewal sent again) is treated as no answer: the primary keeps recording, and its status reads **the standby's answer was not signed and was ignored**. So someone who can interfere with the traffic between the two cannot make the primary stop recording by answering in the standby's place.
- **Both NVRs must run a version that signs answers.** A primary that has been upgraded ignores the answers of a standby that has not, and keeps recording; upgrade the two together.
- **The handback is signed too (#502).** The list of footage to bring back, each file's SHA-256 and size, a "no such footage" and the standby's "handback complete" are each signed as the answer to the request they answer. The primary indexes only footage the standby listed in a signed answer, whose bytes match the signed digest and size (a file longer than its signed size is cut off and refused); it skips footage only on a signed "no such footage", and marks the handback done only on a signed "complete". Anything else is ignored and asked for again at the next pass, with the reason on the primary's failover status. A segment that would take the recordings volume below its headroom is not brought back until there is room.
- **No request can be sent twice.** Each request carries a one-time value covered by its signature; the standby or primary refuses one it has already seen ("The request was sent before"). A request from an NVR that has not been upgraded yet is refused (`426`, "upgrade both NVRs"), but a standby still counts it as the primary being alive, so it does not take over while the primary records; upgrade the two together.
- **Clocks are named.** A request or answer signed with the right secret but more than 60 seconds out is reported as the two clocks differing, with by how much, on the side that refused it, not as different secrets.
- **A standby that never hands back.** While the standby stops its recorders it answers "not yet" and the primary waits, normally for well under a minute. If the answers are still "not yet" after five minutes, the primary records again and raises an incident, *The standby NVR did not hand recording back*, which recovers when the standby grants the lease. Both may be recording in the meantime; recording twice is the lesser fault.
- **Badly signed requests are counted by address** and refused with `429` after twenty in a minute. A correctly signed request is never refused for that, so others behind the same proxy or NAT address as the primary cannot shut out its renewals and make the standby take over from a healthy primary.

## What is copied to the standby

Cameras (with their stream addresses and logins, encrypted under the key both share), camera groups, recording schedules, retention and privacy masks, and the site's time zone and date format. **Not** copied: footage, the footage index and its signing key, users, rules, alarms, notifications, AI settings, integrations, access grants and storage settings. The standby keeps its own users, so people sign in to it with accounts made on it; a camera removed at the primary is switched off and archived on the standby if it holds footage of it, otherwise removed.

## Limits and honest behaviour

- **A partition is not an outage.** A primary that is running but cannot reach the standby keeps recording (a standby that is merely down must not stop it). If the standby cannot hear the primary it takes over after the silence, so **both record the same cameras while the network is split**. The first renewal that gets through ends the takeover and the primary imports the standby's footage; the overlap is duplicate footage, not lost footage. Use a lease and silence long enough that a brief network fault does not cause a takeover, and make sure every camera allows two simultaneous RTSP sessions if a partition must be survivable.
- **Detection takes the silence.** Nothing is recorded between the primary stopping and the standby taking over, except footage the cameras keep themselves (see edge backfill, which the standby does not run for the primary).
- **Clocks.** Keep both NVRs' clocks right (NTP): the silence is measured on the standby's clock and footage times come from both.
- **The lease is advisory while the primary runs.** It stops a primary that has just started (or that the standby holds) from recording beside a standby that is recording; it does not stop a primary that is running and cannot reach the standby. A request cannot be sent twice (its one-time value is remembered by the web process, which serves both the web port and the link's port).
- **One standby, one primary.** More than one standby or primary per secret is not supported. The two NVRs must run the same version (the standby refuses configuration from a newer primary).
- **The standby needs the cameras' network.** A takeover is only as good as the standby's route to the cameras and its storage; check Settings, Failover on the standby after every change of cameras, and exercise a takeover (below).
- **AI analysis, rules and notifications do not run on the standby** during a takeover: it records.
- The configuration is copied in a small sealed file, made for the standby each time it asks (at most one a minute): only the tables a standby copies (cameras, groups, policies, privacy masks, the site's time settings) and the credential key, sealed with the backup passphrase as a backup is. The primary must have a backup passphrase set. It is not a backup: `python -m app.backup restore` refuses it. The file's size does not depend on how much footage the primary has. The standby unpacks it beside its own database, never in the system's temporary folder, and refuses the sync, saying how much room it needs, when there is not room. Only the newest two of these files are kept on the primary, apart from the scheduled, manual and pre-migration backups, which keep their own count (`NVR_BACKUP_KEEP`).

## Exercise it

Before relying on it, with real cameras: stop the primary host (power off, not just the application), time how long the standby takes to start recording (it should be the silence plus a few seconds), check every camera records on the standby, start the primary again, and check that the standby stops, the footage comes back and plays, and both incidents recover. Record the result in `docs/acceptance/roadmap.md`.

## API

Administrators: `GET /api/admin/failover` (settings without the secret, status, takeovers, and `link`: this NVR's fingerprint and link port), `PUT /api/admin/failover` (with `peer_fingerprint`, the other NVR's, and `allow_unencrypted`), `POST /api/admin/failover/link-certificate` (make a new link certificate), `POST /api/admin/failover/sync` (standby: copy the configuration now). The hardening report (`GET /api/hardening`) has `failover_link` while the link is, or may be, unencrypted. Everyone signed in: `GET /api/failover/status`. Between the two NVRs (signed with the failover secret: `X-Failover-Timestamp` and `X-Failover-Signature`, HMAC-SHA256 over the time, method, path and body digest, valid for a minute; a sender that fails the signature 20 times in a minute is refused for the rest of it): `POST /api/inbound/failover/lease`, `GET /api/inbound/failover/backup`, `GET /api/inbound/failover/footage?epoch=N`, `GET /api/inbound/failover/footage/<id>?epoch=N`, `POST /api/inbound/failover/handback-complete`, on the link's HTTPS port (and on the web port, answered there only over HTTPS through a trusted proxy or where an unencrypted link is allowed). Changes to the settings are in the audit log (`failover_settings_changed`); incidents have the fault type `failover` and notify as `system.failure` and `system.recovered`.
